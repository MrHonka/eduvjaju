## Спринт 1: Подготовка инфраструктуры (Linux) (+)
- **Задача:** Сделать из второго ПК управляемый сервер.
- **Что делаешь:** Ставишь чистый дистрибутив Ubuntu Server 26.04.1 на второй ПК (+). Настраиваешь static lease на роутере mikrotik hap ac3. Разбираешься, как мониторить, диагностировать сам ПК (+). Температура, статус дисков (+). Подключаешь дополнительный HDD (+). Уменьшаешь на нём имеющийся NTFS-раздел, размечаешь свободное место под ext4, Монтруешь разделы в ОС (+). Связываешь компьютеры по сети: ssh и Доступ к NTFS-разделу с windows-ПК (+).
- **Итог:** Ты заходишь со своего основного ПК на второй сервер по SSH без пароля (по ключам) и открываешь win-data как папку windows(+).

## Спринт 2: Упаковка приложения (Docker & База данных)

- **Задача:** Научиться правильно изолировать процессы, оптимизировать образы и связывать контейнеры между собой.
- **Что делаешь:**
  - Устанавливаешь Docker Engine и Docker Compose на сервер Kubena из официальных репозиториев.
  - Настраиваешь Docker-демона для работы обычного пользователя без sudo.
  - Выбираешь свое сетевое приложение на C++ (HTTP/TCP сервер) для контейнеризации.
  - Пишешь оптимизированный Dockerfile с использованием Multi-stage build для компиляции С++ (разделяешь среду сборки g++/cmake и среду запуска alpine/distroless).
  - Минимизируешь размер и количество слоев итогового Docker-образа, проверяешь динамические библиотеки (`ldd`).
  - Описываешь `docker-compose.yml` для запуска связки: твой C++ сервис + база данных PostgreSQL/MySQL.
  - Настраиваешь Docker Volumes для сохранения данных БД на жесткий диск в папку `/mnt/k8s-storage`.
  - Пробрасываешь порты приложения наружу и тестируешь доступность сервиса с Windows-ПК.
- **Итог:** Твое C++ приложение компилируется внутри Docker, запускается одной командой `docker compose up -d` вместе с базой данных и сохраняет данные на размеченном HDD.

## Спринт 3: Автоматизация конфигурации (Ansible)

- **Задача:** Исключить ручную настройку серверов и перейти к концепции Infrastructure as Code (IaC).
- **Что делаешь:**
  - Устанавливаешь Ansible на свой основной рабочий ПК (или в WSL/Cmder).
  - Создаешь файл инвентаря (`inventory.ini`) с IP-адресом и доступами к серверу Kubena.
  - Пишешь Ansible Playbook для базовой настройки чистой ОС Ubuntu Server.
  - Автоматизируешь через Ansible: обновление пакетов, создание пользователей, настройку SSH, монтирование дисков в `/etc/fstab`, установку Docker и Samba.
  - Используешь Ansible-переменные (`vars`) и секреты (`ansible-vault`) для безопасного хранения паролей.
  - Проверяешь идемпотентность плейбука (повторный запуск не должен ничего ломать или изменять).
- **Итог:** Полная настройка инфраструктуры сервера Kubena (всё, что мы делали в Спринте 1 и 2) разворачивается автоматически одной командой Ansible с твоего основного ПК.

## Спринт 4: Приватный реестр и CI/CD конвейер (Harbor & Runner)

- **Задача:** Развернуть собственное enterprise-хранилище образов и автоматизировать сборку кода при пуше.
- **Что делаешь:**
  - Разворачиваешь приватный Docker Registry **Harbor** на сервере Kubena через Docker Compose.
  - Настраиваешь самоподписанные SSL-сертификаты, чтобы Docker-демон на сервере доверял твоему Harbor.
  - Создаешь проект в Harbor, настраиваешь права доступа и робот-аккаунты (`Robot Accounts`).
  - Устанавливаешь и регистрируешь локальный воркер автоматизации (GitHub Actions Runner или GitLab Runner).
  - Пишешь конфигурационный файл пайплайна (`.github/workflows` или `.gitlab-ci.yml`).
  - Описываешь шаги CI: триггер по пушу в ветку master -> сборка Docker-образа -> тегирование версией (семантическое версионирование) -> авторизация в Harbor -> пуш образа в Harbor.
- **Итог:** При любом изменении C++ кода и выполнении `git push` робот сам собирает Docker-образ и отправляет его в твой защищенный Harbor.

## Спринт 5: Оркестрация и развертывание Kubernetes (K8s)

- **Задача:** Перейти от одиночных контейнеров к отказоустойчивому оркестратору.
- **Что делаешь:**
  - Устанавливаешь легковесный дистрибутив Kubernetes (**K3s** или **MicroK8s**) на сервере Kubena.
  - Настраиваешь утилиту `kubectl` на основном Windows-ПК для удаленного управления кластером.
  - Создаешь `Secret` в Kubernetes для возможности скачивания образов из твоего приватного Harbor (`imagePullSecrets`).
  - Пишешь базовые манифесты вручную: `Deployment` для запуска C++ приложения, `Service` для внутренней сети.
  - Настраиваешь `ConfigMap` и `Secrets` для передачи конфигурации и доступов к БД внутрь подов.
  - Разворачиваешь Ingress-контроллер (Traefik/Nginx) для маршрутизации трафика к приложению по доменному имени.
- **Итог:** Твое приложение запущено внутри кластера Kubernetes, подтягивает образы из Harbor и доступно по сети, а ты управляешь им со своего ПК.

## Спринт 6: Непрерывный деплой по методологии GitOps (ArgoCD)

- **Задача:** Сделать так, чтобы состояние кластера Kubernetes полностью управлялось через Git (Single Source of Truth).
- **Что делаешь:**
  - Устанавливаешь **ArgoCD** внутрь кластера Kubernetes.
  - Создаешь отдельный Git-репозиторий под инфраструктурные манифесты K8s (инфраструктурный репозиторий).
  - Подключаешь инфраструктурный репозиторий и приватный Harbor к интерфейсу ArgoCD.
  - Создаешь сущность `Application` в ArgoCD, настроив отслеживание (polling/webhooks) изменений в Git.
  - Тестируешь полный GitOps-цикл: меняешь вручную версию тега Docker-образа в манифесте Git -> коммит -> ArgoCD видит расхождение (OutOfSync) -> автоматически обновляет приложение в Kubernetes до новой версии.
- **Итог:** Полноценный продакшн-пайплайн. Достаточно изменить версию приложения в Git, как ArgoCD сам раскатывает новый код в Kubernetes без твоего ручного вмешательства.
